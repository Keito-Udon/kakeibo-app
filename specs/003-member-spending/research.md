# Research: メンバー別の使用額の可視化

Phase 0の技術調査。技術スタックは001・002から変更しない（新規の依存パッケージなし）。本機能で決める
必要があるのは、(1) スマホの幅での配置（FR-005とSC-003の両立）、(2) 集計の置き場所、(3) 割合の
計算と表示、(4) メンバーの色の決め方である。

## 1. スマホの幅での配置（FR-004, FR-005, FR-006, SC-003）

**Decision**:

| 画面の幅 | 左の列 | 左の列とカレンダーの間 | 画面の左右の余白 | 日付マスの金額の文字 |
|---|---|---|---|---|
| 640px未満（スマホ） | 88px | 4px | 8px | 10px・字間を詰める |
| 640px以上 | 176px | 12px | 16px（002と同じ） | 11px（002と同じ） |

左の列はメンバーごとに、表示名（省略せず折り返す）、支払額（「123,456円」、省略しない）、割合の棒、
割合（「81%」）を縦に並べる。

**Rationale**（2026-09-23 に試作ページで計測。試作は計測後に削除）:
- 実際のカレンダーと同じマス構成・同じ金額表記で、横幅390px・360pxの2種類を撮影し、日付マスの金額が
  マスの幅からはみ出すかを測った

| 横幅 | 左の列 | 余白 | 金額の文字 | 1マスの幅 | はみ出した金額 |
|---|---|---|---|---|---|
| 390px | 96px | 16px | 11px | 35px | 「9,999」 |
| 390px | 88px | 8px | 11px | 38px | なし |
| 360px | 88px | 8px | 11px | 34px | 「3,480」「9,999」「12.3万」 |
| 360px | 80px | 8px | 11px | 35px | 「9,999」 |
| 360px | 88px | 8px（隙間4px） | 10px・字間詰め | 35px | なし |
| 390px | 88px | 8px（隙間4px） | 10px・字間詰め | 39px | なし |

- 88px あれば「123,456円」が1行に収まり、長い表示名も3行ほどの折り返しで読める。これより狭くすると
  7桁（「1,234,567円」）が2行に折り返す頻度が増える
- 360pxの端末でも日付マスの金額がはみ出さないよう、スマホでは金額の文字を10pxにする。390pxでは
  11pxでも収まるが、端末の幅で文字の大きさを細かく切り替えるより、スマホでは一律10pxにする方が
  単純（憲法I）
- 640px以上（タブレット・パソコン）では幅に余裕があるため、左の列を広げ、002と同じ文字の大きさに戻す

**Alternatives considered**:
- 左の列 96px・余白16px（最初の案） — 390pxでも「9,999」がはみ出したため不採用
- 名前や金額を省略して列を細くする — spec の Q1 で「省略しない」と決定済み
- 360px未満の端末への対応 — 現在の主要なスマホは360px以上のため対象外とする（plan.md の Constraints に記載）

## 2. 集計の置き場所（FR-001, FR-007, FR-008）

**Decision**: 002の `GET /api/groups/{groupId}/months/{yearMonth}` のレスポンスに `memberTotals` を
追加する。カレンダーは既にこのAPIを3秒ごとに取得しているので、同じ取得で左の列も更新される。
集計は `lib/member-spending.ts` に、DBから読む部分と、割合を計算する純粋関数に分けて置く。

**Rationale**:
- カレンダーと左の列は同じ月・同じグループの数字であり、1回の取得でそろえれば、両者の数字が食い違う
  （SC-002違反）瞬間が生まれない
- 新しいAPIを増やさないので、ポーリングの回数も増えない
- 支払者別の合計は、`ExpenseRecord` を `spentOn` の月と `paidById` で絞り込んで `groupBy` すれば得られる。
  データの保存方法の変更は不要

**Alternatives considered**:
- 別のAPI（`GET .../months/{yearMonth}/members`）を作る — 取得が2本になり、カレンダーと左の列の更新時刻が
  ずれる可能性がある

## 3. 割合の計算と並び順（FR-002, FR-003, Edge Cases, Assumptions）

**Decision**: 純粋関数 `computeMemberShares(members, totalsByUserId)` で次を行う。
- 全メンバーを含める（支払額0円のメンバーも含む。FR-003）
- 割合 = `Math.round(支払額 / 月の支出合計 × 100)`。月の支出合計が0円なら割合は `null`（「支出なし」表示）
- 並び順は支払額の多い順、同額なら先にグループに参加した順

**Rationale**: 四捨五入で合計が100%にならないことは spec の Edge Cases で許容済み。純粋関数に分けることで、
0円・同額・丸めのケースをユニットテストで網羅できる（憲法II）。

## 4. メンバーの色（Assumptions: 月を移動しても色が変わらない）

**Decision**: グループに参加した順（`joinedAt` の昇順）で、決まった6色の並びから色を割り当てる。
7人目以降は先頭の色から繰り返す。

**Rationale**: 参加順はグループの中で変わらないため、月を移動しても、支払額の順位が入れ替わっても、同じ
メンバーは同じ色になる。支払額の順で色を決めると、順位が変わるたびに色が変わってしまう。

## まとめ

| 項目 | 決定内容 |
|---|---|
| 新規依存 | なし |
| データ構造の変更 | なし（既存の支出記録から集計） |
| API | `GET .../months/{yearMonth}` に `memberTotals` を追加 |
| 配置 | スマホ: 左の列88px・余白8px・日付マスの金額10px ／ 640px以上: 左の列176px |
| 割合 | 整数%、月の支出0円なら「支出なし」 |
| 色 | 参加順に6色を割り当て |

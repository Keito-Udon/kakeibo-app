# Feature Specification: 共有家計簿（Shared Budget）

**Feature Branch**: `001-shared-budget`

**Created**: 2026-09-18

**Status**: Draft

**Input**: User description: "半同棲・新婚カップル(2人)が、共有財布の支出を記録・可視化できるWebアプリを作りたい。ユーザーはメールアドレスでアカウントを作りログインし、パートナーをグループに招待して2人で同じ家計簿にアクセスする。2人はそれぞれ支出（誰が・いくら・何に・現金かモバイル決済か）を記録でき、同時に閲覧・編集できる。トップ画面では毎月の設定予算（例: 2万円）に対する残額が一目でわかる。データはグループ外の第三者には公開されない。"

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 支出の記録とグループ共有閲覧 (Priority: P1)

グループのメンバーが支出を記録すると、パートナーもすぐに同じ記録を確認できる。これまでは一方のメンバーだけが全ての支出をアプリにまとめて入力しており、もう一方は現状を把握できていなかった。この機能により、支出が発生した際にどちらのメンバーでも記録・閲覧ができ、管理の負担が一方に偏らなくなる。

**Why this priority**: 現状の最大の課題（管理負担の偏り・同時閲覧不可）を直接解決する、このアプリの中核価値。これがなければ他の機能を実装しても既存アプリに対する優位性がない。

**Independent Test**: メンバーAが支出（金額・内容・支払者・支払い方法）を記録した後、メンバーBが自分のセッション/端末から同じ記録を確認できることをテストできる。これ単体でも「共有台帳」としての価値を提供する。

**Acceptance Scenarios**:

1. **Given** メンバーAとメンバーBが同じグループに所属している、**When** メンバーAが支出（金額・内容・支払者・支払い方法）を記録する、**Then** メンバーBがその記録を自分の画面で確認できる
2. **Given** グループにまだ所属していないユーザーがいる、**When** そのユーザーが招待を受けてグループに参加する、**Then** そのユーザーはグループの既存の支出記録を閲覧できるようになる
3. **Given** メンバーAが支出記録を追加中である、**When** メンバーBが同時に別の支出記録を追加する、**Then** 両方の記録が失われることなく保存される
4. **Given** メンバーBがトップ画面を開いたままにしている、**When** メンバーAが支出記録を追加・編集・削除する、**Then** メンバーBは画面を再読み込みすることなく、数秒以内にその変更を確認できる
5. **Given** メンバーAが追加した支出記録が存在する、**When** メンバーBがその記録を編集または削除する、**Then** 変更が反映され、メンバーAの画面にも数秒以内に反映される

---

### User Story 2 - 月次予算残額の可視化 (Priority: P2)

グループで設定した月次予算（例: 2万円）に対して、当月の支出合計と残額をトップ画面で一目で確認できる。

**Why this priority**: 「使いすぎに気づかない」という副次課題を解決する。P1（記録・共有）があって初めて意味を持つため、P1に次ぐ優先度とする。

**Independent Test**: グループに月次予算額を設定し、複数件の支出を記録した状態でトップ画面を開き、残額（予算 − 当月支出合計）が正しく表示されることを確認できる。

**Acceptance Scenarios**:

1. **Given** グループの月次予算が20,000円に設定されている、**When** 当月の支出合計が12,000円である、**Then** トップ画面に残額8,000円が表示される
2. **Given** 当月の支出合計が月次予算を超えている、**When** メンバーがトップ画面を開く、**Then** 残額がマイナスとして分かりやすく表示される
3. **Given** 月が変わった、**When** メンバーがトップ画面を開く、**Then** 当月分の支出合計・残額として再計算された値が表示される（前月分の支出は当月の集計に含まれない）

---

### User Story 3 - 支払い方法の記録（現金／モバイル決済） (Priority: P3)

支出を記録する際に、現金かモバイル決済かを選択して記録できる。

**Why this priority**: 現状「モバイル決済にすると管理が煩雑になるため現金運用に留めている」という課題への対応であり、価値はあるが前2つのストーリーが機能して初めて意味を持つ付加要素のため、P3とする。

**Independent Test**: 支出記録時に支払い方法（現金／モバイル決済）を選び、記録一覧でその内訳が確認できることをテストできる。

**Acceptance Scenarios**:

1. **Given** メンバーが支出を記録する、**When** 支払い方法として「モバイル決済」を選択して保存する、**Then** 記録一覧にその支出が「モバイル決済」として表示される
2. **Given** 複数件の支出記録が存在する、**When** メンバーが記録一覧を確認する、**Then** 各記録の支払い方法（現金／モバイル決済）が識別できる

---

### Edge Cases

- 支出記録を0円やマイナス金額で登録しようとした場合、システムはエラーとして拒否しなければならない
- グループにまだ2人目のメンバーが参加していない状態（1人のみ）で支出を記録した場合、通常通り記録・閲覧できる（グループ人数の下限を待たずに使い始められる）
- 招待を受けていない第三者がグループのデータにアクセスしようとした場合、拒否される
- 月次予算が未設定のままの場合、残額表示は「未設定」であることが分かる表示になる（0円扱いにして誤解を招かない）
- 招待リンクが意図せず第三者に流出した場合、その第三者もグループに参加できてしまう（リンクの取り扱いはユーザー側の責任とする）
- メンバーAがある支出記録を編集している最中に、メンバーBが同じ記録を削除した場合、メンバーAの編集は失敗として扱われ、記録が既に存在しない旨が分かるようにする

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: システムはユーザーがメールアドレスとパスワードでアカウントを作成できなければならない（MUST）
- **FR-002**: システムはユーザーがメールアドレスとパスワードでログイン・ログアウトできなければならない（MUST）
- **FR-003**: システムはログイン済みユーザーがグループ（世帯）を作成できなければならない（MUST）
- **FR-004**: システムはグループの既存メンバーが新しいメンバーを招待でき、招待されたユーザーがそのグループに参加できなければならない（MUST）
- **FR-005**: システムはグループメンバーが支出記録（金額・内容・支払者・支払い方法）を追加できなければならない（MUST）
- **FR-006**: システムは同一グループの全メンバーが、他のメンバーが追加した支出記録を閲覧できなければならない（MUST）
- **FR-007**: システムはグループ外のユーザーがそのグループの支出記録にアクセスできないようにしなければならない（MUST）
- **FR-008**: システムはグループに対して月次予算額を設定できなければならない（MUST）
- **FR-009**: システムは当月の支出合計と、月次予算に対する残額を算出し表示しなければならない（MUST）
- **FR-010**: システムは支出額として0円以下の値を拒否しなければならない（MUST）
- **FR-011**: システムは各支出記録に支払い方法（現金／モバイル決済）を記録できなければならない（MUST）
- **FR-012**: グループメンバーは、自分が追加したかどうかに関わらず、同一グループ内の支出記録を編集・削除できなければならない（MUST）
- **FR-013**: システムは、あるメンバーが追加・編集・削除した支出記録を、他のメンバーの画面に数秒以内に自動反映しなければならない（MUST）（手動更新やページ再読み込みを必要としない）
- **FR-014**: システムはグループへの招待を、招待リンクの共有によって行わなければならない（MUST）。そのリンクを知っているユーザーであれば誰でもグループに参加できる

### Key Entities

- **User（ユーザー）**: アカウント保持者。メールアドレス、表示名を持つ。1つ以上のGroupに所属できる
- **Group（グループ／世帯）**: 支出を共有する単位。2人以上のUserが所属する（下限は2人を想定するが上限は設けない）。月次予算額を持つ
- **ExpenseRecord（支出記録）**: 金額、内容（メモ）、支払者（Userへの参照）、支払い方法（現金／モバイル決済）、記録日時、所属するGroupへの参照を持つ

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 新規ユーザーがアカウント作成からパートナーのグループに参加するまでを5分以内に完了できる
- **SC-002**: 支出を記録した本人以外のメンバーの画面に、操作なしで数秒以内にその変更（追加・編集・削除）が反映される
- **SC-003**: 月次予算に対する残額表示が、実際に記録されている支出合計と常に一致している（表示のズレ・不整合が発生しない）
- **SC-004**: メンバーが1件の支出を記録する操作を30秒以内に完了できる

## Assumptions

- グループの人数は最低2人（カップル/夫婦）を想定するが、システム上の上限人数は設けない
- 月次予算はグループ単位で1つ設定し、暦月（1日〜末日）ごとにリセットされる
- 支出記録の編集・削除はグループ内の誰でも行える（相互訂正のしやすさを優先し、誤操作のリスクは受け入れる）
- グループメンバー間の変更反映はリアルタイム同期とする。実現方法（ポーリング／WebSocket等）は `/speckit-plan` で検討する
- グループ招待は招待リンクの共有方式とする。リンクの発行者以外への流出対策（有効期限・失効等）が必要かどうかも `/speckit-plan` で検討する
- 使いすぎの通知・アラート機能（プッシュ通知等）はこのフェーズのスコープ外とし、残額表示（マイナス表示を含む）のみで対応する
- 立て替え精算、レシートOCR読み取り、カテゴリ別集計・グラフ、定型支出の自動登録は本フェーズのスコープ外（将来のフェーズ候補）
- 認証方式はメールアドレス＋パスワードによる標準的なセッションベース認証とする
- データはグループ外の第三者に一切公開されない（グループメンバー以外は支出記録にアクセスできない）
